# T8 demo access integration

T8 implements the later build-handoff ruling: demo unlock first, without Stripe. No payment is created or verified, no card is collected, and no subscription is started. Prices in the access card describe planned products. Stripe checkout and `/success` verification remain deferred.

## Run locally

Set `DEMO_UNLOCK_ENABLED=true` in `.env.local` (or the environment of the dev process), then start `npm run dev`. Open `/`, choose **Check my numbers**, then **Try Dani’s family** at the top of the form (or enter household inputs), then go to `/plan` (`/unlock` redirects there) and choose **Unlock Year demo — free**, review instructions, check proofs, then open **Tax-preparer export** and use **Print / Save as PDF**.

The exact string `true` enables grants; missing, false, or differently cased values disable them in every environment. The flag is server-only. Enabling it in production deliberately allows every visitor with a saved household to grant themselves demo access. Production still requires the existing Upstash configuration; development can use T6's memory store. Changing the flag prevents new grants; it does not revoke previously stored, unexpired access.

## T7 merge points

- `requestDemoUnlock` dispatches `cliffguard:access-changed` (`notifyAccessChanged` in `@/lib/planEvents`) after a successful grant. Only T7's plan preview listens, so it drops its locked cards; `PlanAccess` keeps refreshing itself through `onUnlocked` and ignores this event, so it refreshes once.

- T8 deliberately does not create or change `/plan/page.tsx`, result/gig components, or T6's plan/progress/household routes. `src/app/plan/layout.tsx` renders the T7 page followed by the reusable `PlanAccess` panel. The panel is hidden on `/plan/export`. `/unlock` is a legacy redirect to `/plan`.
- The panel fetches `GET /api/plan/access` on mount, explicit **Refresh full details**, successful unlock, and a plan-change event. All protected content is computed server-side. Requests use `no-store`, and stale responses are ignored.
- `src/lib/api.ts` is the small expected merge point: add `PATCH` to `sendJson`'s method union and keep the `notifyPlanChanged()` call after successful `/api/plan` or `/api/gig-check` requests. (The plan preview now suppresses these per-call notifies and emits one `cliffguard:plan-changed` per save; a demo unlock emits `cliffguard:access-changed` through `notifyAccessChanged()` instead.) If T7 uses another API client, import `notifyPlanChanged` from `@/lib/planEvents` and call it **after a successful request has saved preferences or the gig**. Equivalent event: `window.dispatchEvent(new Event('cliffguard:plan-changed'))`.
- Do not emit on every toggle before its server write finishes. Preserve T7's newest-response gate when multiple preference requests are in flight. T8 keeps the current plan visible while refreshing and replaces it when the new read arrives.
- T6's `POST /api/plan` saves `keepMyCash` and `leverOrder`, but does not save its request's `gig`. T8 details and export use the saved `household.lastGig`. T7 must pass that same saved gig to `/api/plan`; changing a gig requires a successful `/api/gig-check` first, which persists it. T8's read endpoint never writes preferences or resets `lastGig`.
- The export uses a normal document navigation so the server checks current entitlement and reads current stored inputs, preferences, gig and proof state. It redirects to `/plan` without active access. Before T7 merges, that redirect destination does not have a page; authorized access to `/plan/export` works once the plan is unlocked.

## Entitlement and progress contract

`POST /api/demo-unlock` accepts exactly `{ product: 'rescue' | 'year' }`, requires an existing household, rejects foreign origins, and uses T6's generic rate limiter at 10 attempts/hour/session. Dates and identity are server-controlled. The response exposes only demo mode, product and the last access date, never the session id or internal grant identifier.

Demo grants fit the existing validated `HouseholdRecord.entitlement`. `stripeSessionId` contains a random `demo_…` identifier and `paidAt` is the grant timestamp solely for compatibility with T6's field names; these fields are not evidence of payment. Rescue ends October 15, 2027; Year ends 365 days after grant, using T6's New York access-date convention. Same-product retries and active Year grants are idempotent. An explicit Rescue-demo → Year-demo upgrade is allowed and never shortens access. Active real paid access is preserved. Expired access can be renewed; already expired fixed-date Rescue grants are refused.

Proofs and done state persist through the existing `PATCH /api/plan/progress`. The panel shares one request coordinator across proof saves, initial demo grants, Rescue → Year upgrades and refreshes. It disables every checklist while saving, retains previous checks on failure, and shares lever-level progress between both adults' IRA cards to match T6's schema. The coordinator belongs to `PlanAccess` above its loading/ready branches. Manual and plan-change refreshes wait for pending mutations before reading replacement progress. Refreshes keep the current plan on screen (the loading card is only for the first load), and the explanation resets only when the plan changes. Extra checkbox actions are rejected while a mutation/read is queued or running. Unlock attempts while busy send no request and show a retry message; the user can retry once the current update finishes. `requestDemoUnlock` releases the mutation before invoking the queued success refresh, avoiding a queue deadlock. A fresh server read after a successful grant supplies both current access and persisted checks. Refreshing cannot discard the mutation lock when checklist children remount.

**T6/T9 helper merge point:** `replaceInput` in `src/server/household.ts` now treats `manual` and `upload` as two entry methods for the same personal household. Switching either way preserves the saved gig (including the export scenario), proof/done progress, check-in history, preferences and entitlement. Crossing `sample_dani` ↔ personal still resets gig, progress and check-ins, while preserving preferences and entitlement as before. Preserve this small helper correction alongside T9's additive provenance header when merging another T6 implementation.

T6 currently reads and writes entire household records without compare-and-set. Panel serialization prevents overlapping proof/grant writes and stale progress refreshes within the same access panel; independent tabs, a preference write from T7, or another external household mutation can still race. Durable cross-request concurrency control belongs in T6's storage/update contract and is not introduced here.

## T10 explanation integration

The entitled `/plan` access panel now includes **Explain my plan**. Without an API key, or when Claude is disabled or unavailable, it returns the real deterministic engine template, expanded to three paragraphs and labeled **Calculation-based explanation**. Set `ANTHROPIC_API_KEY` and restart to enable live explanations; no-key templates never enter the live cache. `CLAUDE_ENABLED=false` forces template mode. The existing `CLAUDE_DAILY_CALL_CAP` controls provider calls, including grounding retries, and forces template mode at exhaustion even for cache hits.

`POST /api/explain` accepts only `{}`, checks active Rescue or Year access, and uses `planExport` to compute exactly the saved gig and preferences. It allows ten requests per hour per session, including cached/template reads. Valid provider explanations are cached for 24 hours in one server-only session envelope at `cg:explain:<sid>`, containing the full SHA-256 calculation hash and validated explanation. A different hash replaces that envelope; only the current calculation needs caching. This keeps session/full-hash isolation while making every cached financial explanation discoverable without scans or an index. The envelope remains separate from `HouseholdRecord`, so cache writes cannot overwrite household progress. No migration is needed: this preview has never had a live provider key or deployed live-AI cache.

Before a provider result is cached, the route rechecks household identity, current access and the complete calculation hash. It checks again after awaited cache storage and removes any late write if deletion or another invalidating change occurred during storage. `deleteHousehold` removes the household first, then the known explanation key; a storage failure propagates and the deletion endpoint does not acknowledge success or expire the cookie. Provider completion after deletion cannot repopulate the cache. No household record, session identity, upload, or extraction evidence is passed to Claude.

The SDK receives structured output generated from the existing explanation schema, with a 900-token cap. Invalid schemas or move IDs fall back. A numeric grounding failure gets at most one retry within the same 15-second deadline. Text is rendered as plain React text. The component remounts on the access panel's read revision and immediately invalidates on plan-change events, including while the parent's mutation coordinator waits for a proof save.

Tests use the installed real SDK with a fake transport, so the implementation suite makes no paid calls. Live output quality, mobile browser layout and interaction remain unverified until those environments are available.
