# T11 monthly check-ins

`/checkin` is reachable from the app header and the standalone `/unlock` plan panel. Active Year access enables the form, history, Jan 15 estimate and `.ics` download. Empty sessions get entry links; Rescue and expired access get the Year preview and upgrade/renewal link. `/unlock` remains the plan destination until T7 merges. The T10 explanation component and existing panel mutation coordinator are preserved. This implementation supersedes the check-in/calendar deferral in the earlier T8 integration note.

## HTTP contracts

All new endpoint responses, including errors, use `Cache-Control: no-store`. Mutation endpoints reuse the shared same-origin helper and strict Zod request objects. Only the session cookie identifies a household.

- `GET /api/checkin`: `{ kind: 'empty' }` without a household, `{ kind: 'locked', householdScope }` without active Year, otherwise `{ kind: 'ready', householdScope, asOf, baselineVersion, since, adults, diagnosis, history, schedule }`. `adults` exposes only `id`, `label`, `seExpected`, `wagesExpected`; `schedule` has `due`, `monthLabel`, `nextDate`. Diagnosis is the saved 2026 input with `gig: null`.
- `POST /api/checkin`: `{ received: { seByAdult, wagesByAdult, capitalGains, interestOrDividends }, expectedRestAfter?: { seByAdult, wagesByAdult }, requestId?: string, baselineVersion?: ISO_datetime }`. Adult maps accept only active `a` / `b`. All additions and forecasts are finite, nonnegative and at most $1 billion, except capital gains can be negative within the same magnitude. Annual SE/wage projections and the updated investment totals are also bounded. Unknown properties are rejected. Missing expected-rest entries default to `max(0, old expected - received)`. Response: `{ checkin, diagnosis, alerts, replayed, baselineVersion }`. The baseline version is the saved record's `updatedAt`; stale new writes fail with 400. Server timestamps are monotonic within check-in writes. Server dates use New York. Rate: 30 requests/day/session, including retries.
- `POST /api/checkin/estimate`: exactly `{ expected2027: number }`, between $0 and $1 billion. Returns the unchanged engine `estimate2027` fields `{ floor, cliff2027, headroom2027, warning }`, plus `deferredToNextYear` from the actual current saved plan, including saved gig/preferences. This calculation does not mutate the household. Separate 30/day/session rate limit. The UI rounds the suggested estimate upward to cents so display cannot understate the floor.
- `GET /api/calendar.ics`: active Year only; attachment `cliffguard-2026.ics`, `text/calendar; charset=utf-8`. Six all-day deadline events cover Dec 15, Dec 31, both Jan 15 obligations, Jan 31 and Apr 15 from the existing engine rules. A seventh event starts on the next first of the month (today if already the first) with `RRULE:FREQ=MONTHLY;COUNT=12`. Every event has -7-day and -1-day display alarms and a `/checkin` link. Lines use CRLF and fold at 75 UTF-8 octets; text is escaped. App URL must be HTTP(S), contain no credentials/newlines, and only its validated origin is used.

Missing-household mutation/calendar calls return 404; non-Year or expired access returns 402; invalid bodies, changed replay payloads and stale baselines return 400; limits return 429 with `Retry-After`. A read deliberately returns a useful empty/locked state without protected numbers.

## Income and retries

A check-in always updates **coverage year 2026**, including after year-end. It never classifies 2027 receipts as 2026 income. Labels distinguish gross wages from self-employment profit after business expenses. Investments are only previously uncounted additions to an annual forecast: interest/dividends are added once to the taxable-interest bucket, while net gains/losses are added once to capitalGainsNet. They are not additional scenario deltas. The expected-rest defaults move forecast income into year-to-date without increasing the projection; unchanged expected-rest represents income beyond the old forecast.

The first delta and alerts compare the saved pre-update diagnosis with the updated diagnosis, both with `gig: null`. Saved gig, preferences, provenance/source, proofs/progress and entitlement survive unchanged. The plan continues using the existing saved gig scenario through the normal plan integration; it is not silently reset by a check-in.

The browser creates a UUID before dispatch, retains the original body/ID after an uncertain save, persists that pending body under a versioned sessionStorage key when available, and generates a new ID after success. The persisted body is scoped to a non-secret, server-created household identity; same-household writes/check-ins preserve scope, while sample/personal replacement rotates it. Older T6 records use their createdAt plus sample/personal category until replacement. Successful household deletion in the shared browser API clears both current and legacy retry storage and notifies mounted forms to clear input/retries and abort pending operations. Successful household replacement invalidates a different scope; check-in reads also reconcile scope before recovery. Unscoped v1 retries are discarded because they cannot safely be attributed to a household. Same-household uncertain saves retain the exact body/UUID despite an updatedAt change. Matching replays return the original diagnosis and alerts without writing the record again. A reused ID with different amounts fails. Retry metadata is optional in `CheckinSchema` so older records still load: `requestFingerprint`, the pre-update `baseline`, and a validated post-update `projectionInput` snapshot make an original response reproducible after later updates. History and its snapshots are capped at 24, newest last.

**T6/T7 serializer boundary:** `publicCheckin` is the shared allowlist used by both the check-in endpoints and `householdView`. Snapshots/fingerprints never leave the server. `householdView.householdScope` is a public, non-secret household lifecycle key, independent of session and entitlement IDs; new records have optional stored `checkinIdentity`, regenerated only at replacement. `householdView.entitlement` exposes only `product` and `validUntil`; session and grant IDs remain private. Its history is empty without active Year access. Existing current household inputs/diagnosis and unrelated response fields keep their prior behavior.

T6 still saves entire records without compare-and-set. Within-page double-click protection, stable IDs and stale baselines protect normal submissions and sequential retries, but simultaneous writes from multiple tabs/servers can race. Retry recognition covers the latest 24 retained check-ins; programmatic clients that omit `requestId` get a new server ID per call and must not treat additive retries as idempotent. Do not describe this as an atomic storage guarantee.
